弱网自动重试（web/src/api/retry.ts） ​

瞬时失败（断网、超时、连接被重置、网关抖动）自动重放，用户不必手点重试；策略与小程序同一套参数：

维度规则
可重放缺省只有 GET / HEAD / OPTIONS；写请求需业务显式声明幂等（{ retry: true }，如带 client_request_id 的 inventory.inbound / inventory.outbound / inventory.reverseOperation）；{ retry: false } 关闭重试（启动路径上的两个 3000ms 探针）
触发条件无 response（连接层失败）或状态码 ∈ 408 / 429 / 500 / 502 / 503 / 504；axios.isCancel 与已 abort 的请求不重试
次数与节奏最多 3 次尝试；失败后退避 600ms → 1800ms（上限 6s），叠加 30% 以内抖动，避免并发请求同时复活
最坏耗时单次 30s × 3 + 退避 ≈ 92s
重放方式复用同一份 config 重发：X-Request-ID 不变、Authorization 重新读取（等待期间 token 可能刚刷新）
拦截器顺序重试拦截器注册在 401 刷新与错误归一化之前：只有它拿得到原始 AxiosError（状态码、取消标记）

请求处理链 ​

中间件在 internal/app 里按 由外到内 注册：真实 IP → 请求上下文（request_id / 耗时头 / 访问日志）→ panic 兜底 → 项目头 → CORS；之后进入 web.H 包装的处理函数。

环节实现
中间件middleware.RealIP() → middleware.RequestContext() → middleware.Recovery() → middleware.ProjectHeader() → middleware.CORS()（internal/app/app.go）；RequestContext 在 RealIP 内层以便日志读到改写后的 IP；CORS 在最内层，NoRoute 的 400 与各类错误体同样带 CORS 头
依赖顺序web.Router.Group(prefix, deps...) 的分组依赖先于路由依赖；习惯顺序为项目（auth.RequireProject）→ 鉴权（auth.CurrentUser）→ 角色（auth.WarehouseWriter 等，内部会先确保已鉴权）→ 其它（deps.RequireFullSecondaryWarehouse）；任一依赖返回错误立即中止，参数尚未校验
参数校验与 422依赖全部通过后，处理函数用 c.Params() 读取路径（PathInt）、查询（QueryStr / QueryInt / Page …）、请求头（IfMatch）、JSON 请求体（Body），每处的错误都追加进同一个列表，最后 p.Err() 一次性返回 *web.ValidationError → 422 VALIDATION_ERROR，details.errors 为 type / loc / msg / input 结构（与 Pydantic 兼容）
先提交再写响应处理函数通过 c.OK / c.Created / c.NoContent / c.File 等只是登记响应；web.H 在函数返回后先 c.DB.Commit() 再写出响应，所以客户端拿到 2xx 时写库已可见；提交失败按数据库错误返回错误体。出错则 Rollback()。处理函数不手动提交，提交后才做的事登记 c.DB.AfterCommit（回滚后的补偿用 AfterRollback）
panic处理函数里的 panic 由 web.H 转成 500 INTERNAL_SERVER_ERROR；中间件层的 panic 由 middleware.Recovery() 兜底
路由细节Gin 关闭 RedirectFixedPath、开启 RedirectTrailingSlash 与 HandleMethodNotAllowed；路由定义沿用契约里的 {item_id} 写法，由 web.Router 转成 Gin 的 :item_id；multipart 内存上限 32 MB（超出部分落临时文件）

乐观锁版本（If-Match） ​

所有带乐观锁的写操作（PATCH/PUT/DELETE/restore）版本号放 If-Match 头而非 query 参数，避免版本号进入访问日志（web.Params.IfMatch，允许带引号）；缺失或非整数时返回 nil，由 service 决定是否强制（apperr.ValidateVersion → VERSION_CONFLICT，details 带 expected/actual）。

中间件与性能响应头（server/internal/middleware） ​

RequestContext 为每个请求注入 request_id（取第一个 X-Request-ID 请求头，截断到 128 个字符，否则生成 UUIDv4）并写访问日志；耗时响应头在响应头写出前一刻补上（包住 ResponseWriter），因此包含事务提交耗时，只计量服务端时间。

响应头含义
X-Request-ID本次请求标识，与日志 request_id 一致
X-Response-Time服务端处理总耗时（毫秒），从进入中间件到写出响应头
X-DB-Time数据库语句执行耗时合计（毫秒），取 min(采集值, 总耗时)
X-Compute-Time总耗时 - DB 耗时（毫秒），含校验/权限/序列化
X-DB-Queries本次请求执行的 SQL 条数（含提交），用于识别 N+1
这 5 个头（加 Content-Disposition）都在 CORS 中间件的 Access-Control-Expose-Headers 中，跨域时可读。
中间件规则
RealIP取可信边缘代理给出的真实 IP，优先级 EO-Connecting-IP → X-Real-IP → X-Forwarded-For 的第一段；候选值需能被 net.ParseIP 解析，全部无效则用连接的远端地址
RequestContextrequest_id、DB 计时器、耗时响应头、访问日志（见「日志与 request_id」）
Recovery兜底中间件层未捕获的 panic，响应尚未写出时返回 500 INTERNAL_SERVER_ERROR
ProjectHeader把可解析的正整数 X-Project-Id 落进请求上下文（只解析、不查库）；web.H 新建会话时据此设定项目，真正的校验由 auth.RequireProject 完成
CORSReferer 优先（兼容不发 Origin 的内嵌 WebView/微信），无效或缺失回退 Origin；Referer: null 原样返回 null。白名单（APP_CORS_ORIGINS）为空表示不限制；否则需 origin 精确命中、或 *、或与 host 相同、或 allowed 以 . 开头时按 host 后缀匹配（.example.com 匹配 app.example.com）；未命中不回显 CORS 头。预检（OPTIONS + Access-Control-Request-Method）直接 200，方法白名单 DELETE, GET, HEAD, OPTIONS, PATCH, POST, PUT，回显请求的 Access-Control-Request-Headers，Access-Control-Request-Private-Network: true 时回私有网络头；正常响应补 Vary: Origin, Referer
internal/middleware 的单元测试覆盖真实 IP、request_id 与耗时头、CORS 白名单与预检。

项目隔离（server/internal/db + server/internal/auth） ​

业务数据按项目隔离，但不是多租户：没有用户-项目授权表，任何登录用户都能访问全部项目，只是同一请求只能处于一个项目。隔离由「会话上的项目上下文 + 业务 SQL 显式按 project_id 过滤」实现。

机制实现
项目上下文db.Session 携带项目 id 与「系统上下文」标记；auth.RequireProject 校验 X-Project-Id（缺头 400 PROJECT_REQUIRED，非整数 422，项目不存在 / 停用 400 PROJECT_NOT_FOUND / PROJECT_DISABLED）后 c.DB.SetProject(id)
读写过滤项目域表的每条 SQL 都显式写 project_id = ?，项目 id 一律取 s.ProjectID()；列表查询用 common.Where.Scope(s, alias) / s.ScopeFilter(alias) 追加条件；INSERT 写入当前项目 id
fail-closeds.ProjectID() 在未设定项目时返回 400 PROJECT_REQUIRED，绝不静默放行成「看到全部项目」
系统上下文确实跨项目的入口显式进入系统上下文：s.System()（共享同一事务的副本）、db.SystemSession(ctx)（独立会话）、auth.SystemScope（整个请求）；系统上下文里 ScopeFilter 不加项目条件
切换项目s.WithProject(pid) 返回共享同一事务、处于指定项目的副本；后台任务用 db.ProjectSession(ctx, job.ProjectID) 按任务行恢复项目
唯一键项目域唯一键都带 project_id（如 (project_id, plan_no)），编号按项目生成

项目域表清单在 server/internal/model 的 ProjectScopedTables（32 张，删除项目前的数据统计依赖它）；新增业务表必须带 project_id 并登记进该清单，同时改 init.sql 与 Go 模型（AGENTS.md 已写成约定）。

MCP 服务（server/internal/api/mcp） ​

项内容
挂载mcp.Register 在 /api/v1/mcp/ 上接收全部方法；传输为 Streamable HTTP 的无状态 JSON 模式：只接受 POST（GET / DELETE 返回 405，不提供 SSE 流与会话），Content-Type 必须是 application/json，响应为 JSON（支持 JSON-RPC 批量请求，纯通知返回 202）；请求体上限 16 MB；协议版本支持 2024-11-05 / 2025-03-26 / 2025-06-18 / 2025-11-25；serverInfo.name 为 spare-parts-management
工具system_whoami（返回令牌对应用户、角色、当前项目与项目来源）、projects_list（列出全部项目）、operations_list（按标签/关键字列出操作）、operation_describe（返回某操作的参数、请求体、响应契约与参数落位提示 call_arguments）、operation_call（以 X-API-Token 调用业务接口；path_params / query / headers / body / file 分别对应路径参数、查询参数、请求头、JSON 请求体与附件，附件用 file.content_base64 上传，二进制响应超过 25 MB 报错）
操作目录由内嵌契约（server/internal/openapi 的 openapi.Operations()，按契约文件顺序）生成，按 operationId 索引；ExcludedPaths 排除 /api/v1/auth/login、/api/v1/auth/refresh，ExcludedPrefixes 排除小程序专用前缀 /api/v1/mini-program/，其余管理端接口全部可调用。小程序专用接口的能力都由管理端接口覆盖（库存与流水 → /inventory/*、隐患 → /hazards*、精简库存 → /secondary-warehouse、物料编码库 → /material-code-library、项目 → /projects），所以「完整操作所有功能」不依赖小程序端点
参数映射operation_describe 的 call_arguments 由契约派生：path_params / query 是名字列表，headers 是 {name, note} 列表（如 if-match 说明「乐观锁版本号（String(version)）；不传则不校验版本」），body 是请求体 content-type 列表（multipart 时为 null，改用 file），file 是上传表单字段名（固定 file）。headers 只接受契约里该操作声明的请求头；令牌头与项目头（ManagedHeaders）由 MCP 层统一设置，不接受调用方传入
上限请求体上限 16 MB（附件 base64 编码后约 12MB 原文）；单次返回二进制不超过 25 MB，超出报错
调用方式operation_call 用 httptest.ResponseRecorder 把请求在进程内交给应用自身的 Gin 引擎（mcp.SetHandler），仍完整经过中间件、参数校验、角色权限、乐观锁与事务；最多跟随 5 次重定向。带乐观锁的写操作把版本号放进 headers（如 {"If-Match": "3"}），与网页端同一个入口（If-Match 头）
认证取 ?token=、X-API-Token 或 Authorization: Bearer，经 auth.FindUserByAPIToken 命中启用用户后解析项目（X-Project-Id → ?project_id= → 默认项目），失败返回 401 + {"code":"INVALID_TOKEN", ...}
一致性测试internal/api/mcp 的 Go 测试校验：目录不含排除项、排除项仍能命中存活路由、目录 + 排除项覆盖契约里的全部操作；改排除清单时同步本小节

分享带搜索 / 筛选（utils/share.js） ​

环节实现
写各页重写 sharePath()，用 buildSharePath(route, params) 拼 query：空值 / null / undefined 一律省略，其余逐个 encodeURIComponent（中文与 & = # 都不会破坏结构）

  • 登记时检查人员缺省为当前小程序用户姓名，责任人仍由所选责任单位带出快照；client_request_id 是幂等键，重复提交返回同一条隐患而不是新增。
  • 跟进走与网页端同一个更新接口：状态是普通可编辑字段，version 为乐观锁，提交旧版本会被拒（VERSION_CONFLICT）。
  • 图片上传（/mini-program/hazards/images）与网页端共用同一套存储与去重规则，附件管理按两张关联表统计引用次数。
  • 隐患类型与责任单位只在小程序里选择，维护仍在网页端。

弱网自动重试与鉴权失效的静默重登（utils/request.js） ​

请求统一走 utils/request.js：单次 timeout 30s，瞬时失败自动重放，策略与网页端 web/src/api/retry.ts 同一套参数。

维度规则
可重放缺省只有 GET / HEAD / OPTIONS；写请求需业务显式声明幂等（retry: true，出库与隐患登记都带 client_request_id、服务端按键去重）；retry: false 关闭重试
触发条件fail 回调（断网、超时、连接被重置）或状态码 ∈ 408 / 429 / 500 / 502 / 503 / 504
次数与节奏最多 3 次尝试；失败后退避 600ms → 1800ms（上限 6s），叠加 30% 以内抖动
最坏耗时单次 30s × 3 + 退避 ≈ 92s（原先是一次 60s 的默认超时，中途断连只能整单重来）
重放方式复用同一份 options（data 里的 client_request_id 不变），每次重新读取 token，重登后自动带上新凭证
图片上传uploadImage（wx.uploadFile）单次 120s 且不自动重放：包体大、慢，重发会重复建附件

鉴权失效单独走一次静默重登，不占用弱网重试额度（两者计数分开：_attempt 与 _retried）：

登录（auth: false）、绑定注册（显式 token）与写请求不参与自动重放：前者的一次性 code / registration_token 不能复用，后者的副作用由服务端幂等键决定。重试额度用尽后仍按原样抛错，页面提示与改造前一致。

功能模式与运行模式（utils/features.js） ​

每个功能页三档：disabled（隐藏）、query_only（只读）、read_write（可写：库存可出库、隐患可登记与跟进）。模式由服务端设置下发，小程序启动时拉取；拉取失败时回落到「库存可写、隐患可写、其余只读、完整二级库模式」的默认值，避免因一次网络失败把出库与隐患登记关掉。开关只用于小程序前端的入口拦截与展示，后端数据接口不按它鉴权。

台账查看只有浏览能力（列表、搜索、详情都是只读），所以网页端设置里只开放 disabled / query_only 两档，与物料编码库、华星总库存一致；read_write 档在台账上没有任何可写入口，因此不提供。
